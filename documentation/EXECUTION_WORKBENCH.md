# Coding-workbench execution boundary

`@mars/execution` exposes `openRuntimeSession` for the task API. Oh My Pi remains the only agent loop, tool dispatcher and conversation writer. This is a library integration, not a complete workbench or Milestone 1 acceptance claim.

## Integration

The caller supplies a validated task, a private workspace directory, a protected state directory **outside** the workspace, the existing MARS model registry, explicit read/write/execute approvals and `RuntimeTools`. The task API must authenticate the caller, serialize runs for a task, enforce its scope/revision and provide the workspace implementation. The callback methods are a trusted host boundary, not a sandbox. Never supply unrestricted host filesystem or shell callbacks in production.

Only approved host-bound `mars_*` custom tools are registered. Oh My Pi's built-in tools are never enabled. Ambient tools, extensions, project instructions, MCP, LSP, IRC, custom-tool discovery, prompt-cache warming, title generation and automatic model substitution are disabled. The active tool set is verified after initialization. The workspace provider must enforce path confinement and secret exclusions independently, and execute commands in its verified no-network container boundary. There is no host-shell fallback in this package.

### File reads and edits

Each model may set `editFormat` in `models.json`: `hashline`, `replace`, or `apply_patch`. Defaults follow omp 18.14.0: hashline except Kimi, MiMo, MiniMax, DeepSeek, StepFun, Codex Spark, GLM 5.3 Flash and Qwen 3.8, which use replace. Matching is case-insensitive on the model id and upstream model name. These are upstream defaults, not MARS-measured recommendations. Sources: omp's [`src/utils/edit-mode.ts:22–44`](https://github.com/can1357/oh-my-pi/blob/31147f9d1a76608549821c3759f8487b4d66c72d/packages/coding-agent/src/utils/edit-mode.ts#L22-L44), [`src/edit/settings.ts:40`](https://github.com/can1357/oh-my-pi/blob/31147f9d1a76608549821c3759f8487b4d66c72d/packages/coding-agent/src/edit/settings.ts#L40), [`CHANGELOG.md:143`](https://github.com/can1357/oh-my-pi/blob/31147f9d1a76608549821c3759f8487b4d66c72d/packages/coding-agent/CHANGELOG.md#L143), and pi-catalog's identity/taxonomy files listed in `packages/execution/src/edit-format.ts`. No pi-catalog dependency or ambient omp setting is used.

`apply_patch` without a host patch applier falls back to hashline while retaining `requested: "apply_patch"`. The runtime exposes `{format, requested, source}` as `editFormat` and appends one `mars.edit_format` journal entry per open, without changing the resume binding. On launch and resume, the workbench stores that selection as optional `edit_format` in protected `launch.json` (old launch files remain readable), and makes one best-effort task-event append through `workbenchEvent({operation: "edit_format.selected", model_id, format, requested, source})`. An unavailable event sink does not fail launch. These records are evidence for a future benchmark, not evidence of a measured improvement.

Only the selected edit tool is exposed: `mars_edit`, `mars_replace` (unique exact `old`/`new`, or `replace_all`), or `mars_apply_patch` (host patch applier). All require both read and write approval. `mars_write` remains available with write approval. `mars_edit` and `mars_replace` use only `RuntimeTools.read/write`; valid UTF-8 input and result files are limited to 1 MiB, total edit content to 128 KiB. Before the single successful write, the runtime re-reads and compares bytes. Changed bytes are revalidated with the same operations against the fresh content; failures return their message and bounded recovery together. At most three reads are made; without two consecutive identical reads, the edit rejects with bounded recovery around the first anchor or plain replacement rows, not the whole file. This is a pre-write re-read comparison, not provider-level atomic compare-and-swap: a race remains between the final read and write. Anchored edits preserve BOM, detected CRLF/LF and final-newline state; mixed endings normalize to the first break. Host pre/post-tool hooks retain the actual `mars_edit` or `mars_replace` name on each read/write, through the same workspace provider, approvals, claimed-path and privacy boundaries.

Hashline rows are `<line>:<hash>|<text>`, with one-based line numbers. The hash is the low 15 bits of `Bun.hash.xxHash32` of the exact line text (whitespace significant), encoded low-five-bit group first as three characters from `abcdefghijkmnpqrstuvwxyz23456789` (32 alphanumeric symbols, excludes `0/o/1/l`). Tags do not depend on the line number. This is the per-line idea from [the hashline post](https://blog.can.ac/2026/02/12/the-harness-problem/), not omp 18.14's per-file four-hex tag; per-line tags let edits address individual lines without reproducing old text. A 15-bit hash is not cryptographic: a changed line can collide with probability about 1/32768, and no effectiveness benchmark has been run.

`mars_edit {path, edits}` accepts up to 100 strict operations:

- `replace {anchor, end?, content}` replaces one line or an inclusive range; `delete {anchor, end?}` removes it.
- `insert_before` / `insert_after {anchor, content}` insert beside a line; `BOF` / `EOF` name the file boundaries and support empty files.
- Operations execute sequentially and atomically in memory. An anchor resolves by the current numbered line and/or the surviving original line's tracked origin, requiring a matching hash. Exactly one distinct match resolves; two are ambiguous, none stale. An end before its start is invalid. Any failure aborts the call without a write.
- Anchor strings tolerate surrounding whitespace and pasted `|text`. Content splits on LF with CR removed, drops exactly one final LF, and an empty string inserts one empty line. If every content line has an anchored prefix, those prefixes are stripped.
- Recovery uses fresh rows around the anchor's original line number ±5 lines, plus ±2 around up to three other occurrences of its hash; bounded to 60 rows / 8 KiB, cutting at row boundaries. Success includes bounded changed regions (±1 context, 40 rows) for chaining. Exact replacement failures use bounded plain `line|text` rows; ambiguous replacements ask for surrounding context or `replace_all`.

`mars_read` accepts optional `offset` (1-based first line) and `limit` (1–2000 lines). Hashline reads include a range header and `line:hash|text` rows; empty files instruct insertion at `BOF`. Other formats keep the original raw-text behavior and 128 KiB limit when no range is supplied. Ranges allow files up to 1 MiB and include a header. Output is bounded to 128 KiB, cutting at row boundaries with a continuation offset. Hosts using `initialRequestAllowance` or `optionalInstructionCapacity` may pass the effective `editFormat` for exact tool accounting; omitting it reserves the largest eligible edit-tool declaration.

Automatic model selection uses an available tool-capable model in the configured default route and skips paid models even if the user's registry permits paid routing. Explicit paid selection requires `allowPaid` and known input/output prices. The selected model is pinned to the persisted session: the host rebinds only when a specialist resume moves to its routed fallback after the pin is invalidated, or to a changed serving binding of the same pin, recorded in `model_rebinds`. This first execution bridge supports text and function tools, not images or portable reasoning blocks.

## Persistence and recovery

Keep `journalPath` and `sessionId` in the task service's protected runtime reference. Resume by supplying that same journal path; it must reside under the runtime state directory. The journal binding checks task/session/scope, workspace, model and unchanged budget. Oh My Pi's original journal is the authoritative conversation. Task event adapters should store `RuntimeObservation` journal/entry references and lifecycle metadata, not become another conversation writer. Stream observations do not assert an entry has already been committed; consumers reconcile against the journal after `run` returns and flush completes.

Recovery rejects a missing or invalid persisted budget rather than replenishing the allowance, and closes the reopened journal on validation failure. Cancellation still flushes the journal if stopping a workspace fails. Disposal independently attempts workspace stop, SDK disposal, provider unregistration and auth release before reporting a sanitized cleanup failure. Provider dispatch defaults to the registry's environment, limited to the selected provider's credential reference; callers do not need to repeat credentials in runtime options.

`mars.budget` journal entries reserve an allowance before every model dispatch and settle only after a successful stream. Failed/ambiguous requests retain their reservation. The original wall-clock deadline survives restart; resume does not refill the budget. Serialized transport UTF-8 bytes plus overhead provide a conservative input allowance, not an exact tokenizer measurement. Output is provider-limited using `maxTokens`; missing usage retains the full reserved output allowance. Unexpected reported usage fails the run instead of being silently accepted. This accounting is not an independently verified provider invoice or a guarantee that a third-party service honors its declared price/token limits.

Cancellation aborts the provider transport and asks the workspace provider to stop its process tree. A cancelled controller cannot dispatch another run; reopening its durable task/session is a separate, policy-controlled operation. Observation persistence failure prevents subsequent model/tool dispatch. A `completed` outcome means the agent returned normally, **not** that independent acceptance tests passed. The task service must expose checks actually run and remaining unverified criteria separately.

## Host-owned verification verdict

`completed` is an execution status: the Oh My Pi session ended normally. It is not evidence that the requested output exists (`documentation/evidence/ollama-textual-tool-call.md` records a live run that ended `completed` with the model's tool call written as plain text and the file absent). Verification is a separate verdict owned by the workbench host:

- **Declared before the run, outside the model's control.** `tasks.start` accepts `required_checks` (`@mars/contracts` `RequiredCheckSchema`: today `file_content` with a relative `path` and `sha256` or `content`, optional `timeout_ms` ≤ 60 s). They are frozen into `launch.json` in digest form only (`sha256`, never the expected bytes, so an accepted start always yields a readable launch); the model never sees or edits them, and a run without them is never verified.
- **Evaluated by the host after the run on an immutable candidate.** When the outcome is `completed`, `host.ts` re-reads the workspace (`WorkspaceRef.revision`, the provider's tree digest), reads each required path through the workspace provider with a bounded timeout, and re-reads the revision afterwards. Missing file → check `failed` (`Required file missing: <path>`); wrong bytes → `failed` (`Required file content mismatch`); timeout or a provider error → `inconclusive`, never `passed`; a revision that moved during the checks → `inconclusive`; a candidate that cannot be acquired at all → an `inconclusive` record with `candidate: null` and no check results (still evidence, never silent "unverified").
- **Persisted with existing contracts.** The verdict is a `tool.completed` task event from `@mars/workbench` whose payload is a `VerificationEvidenceRecord` (`operation: "verification.verdict"`, run id, task revision, candidate `{workspace_id, provider, revision}`, per-check results, reasons, diagnostics such as a tool call emitted as text, `verified` = every check passed). It is written before the task turns `completed`, so a client that sees the terminal status also sees the evidence.
- **Presented through one rule.** `verificationStateFor(candidateRevision, records)` in `@mars/contracts` yields `verified` only for a passed verdict on the exact candidate revision; `failed`/`inconclusive` for the latest verdict on that revision; `stale` when evidence exists only for another revision (e.g. after a restore); `unverified` when no verdict exists. `tasks.verification` returns the current candidate, the records and that state; the VS Code client recomputes the state from the records itself and shows "Verified", "Verification failed", "Verification inconclusive", "Verification stale" or "Unverified" beside the task status. Team Chat result sharing should consume the same verdict.

Textual tool calls are never parsed or executed; tools run only through validated structured calls (`packages/providers/src/models/ollama-trace.test.ts` shows the adapter keeps structured `tool_calls` even when `content` is present).
