# Proposal: Install verified extensions from VS Code through Workbench

## Decision requested

1. **Who can call it?** A client with the current Workbench bearer and exact server-owned project scope can list, request, and track an install on an opted-in local Workbench. The MARS VS Code extension host is the intended client, not a privileged identity: another holder of that bearer can also request an install. **No RPC caller can approve it, install anything directly, or issue an MCP grant.**
2. **What replaces the native approval step?** The operator explicitly approves in a separately launched, foreground host terminal that the requesting client cannot drive. Desktop and terminal prompts render the same structured review plan, including the project, permissions and grant duration or skill changes. Unapproved requests expire after five minutes. If terminal isolation or foreground checks cannot be assured, installs stay off until an independent approval broker or native prompt exists.
3. **Does it reuse the same catalog and grant/revocation path?** Yes. Desktop and Workbench ship the same release-owned catalog and SHA-256-pinned payloads from [desktop PR #246](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/pull/246), not two copies of the definitions. MCP uses the existing host-signed review, grant, loader, and `mars mcp revoke` path in the target project's private state. Skills and plugins use that Workbench's existing skill store; plugins are bundles of instructions, not executable extensions.

**Status:** Proposed for design review. This does not change #246, the [VS Code redesign PR](https://github.com/ronavkarumsi04/MARS-Send-Youre-AI-To-Space/pull/10), or any runtime behavior.

## Scope and baseline

The first release supports a single-user, local `mars serve` instance launched by its operator with an explicit flag (proposed: `--verified-extensions`) from a separate foreground host terminal. The desktop managed Workbench keeps using its native dialog and IPC. VS Code Remote, remote or shared servers, forwarded/proxied deployments, remote execution workspaces, and unattended processes are not supported. No marketplace, third-party downloads, URLs, executable plugin hooks, automatic updates or grant renewals, global installation, or Assistant chat tool enablement are proposed.

Today [Workbench RPC](WORKBENCH_RPC.md) is a loopback JSON RPC server with a per-start bearer and exact scope checks. The [VS Code transport](../apps/vscode/src/extension.ts) captures the bearer from SecretStorage on connect. Neither mechanism identifies a human or proves that a dialog appeared. The desktop installer has a trusted native confirmation before the Workbench receives a catalog ID over its private channel. This proposal preserves that separation using an operator-controlled terminal rather than teaching the Workbench to trust a client assertion.

## User flow and approval boundary

1. The operator opens a host terminal outside VS Code and the agent runtime and starts the opted-in Workbench themselves. The requesting client must not have access to that terminal's input. Startup requires usable project-private stores and an interactive controlling terminal for both the prompt and input, with Workbench in the foreground process group (or equivalent verifiable OS control). A pipe, redirected input or output, detached process, or missing foreground check disables approval.
2. In a trusted, local desktop VS Code workspace, the extension host discovers support and shows the Workbench's project label and catalog. A deliberate **Request install** click sends a catalog ID; the host validates it against the current catalog and attachment. The page shows a short, expiring review code and tells the operator to switch to the Workbench terminal. It does not open a terminal, paste or run a command, or display an `Approve` action.
3. The operator enters the code in Workbench's review prompt. Incoming requests do not pop a prompt or print arbitrary text. The code selects a request, not a permission. Workbench renders the host-built review plan below and checks that it still owns the original foreground terminal before rendering and again when consuming the explicit **Add to project** choice. Loss of foreground or terminal input invalidates the displayed review; a buffered reply or regaining foreground cannot approve it. Cancel, Enter without a choice or timeout also prevents approval.
4. Workbench consumes the approval internally and executes the reviewed plan once. VS Code polls for the result using the original connection and refreshes the catalog. New tasks can use the installed content; an existing task's tool or instruction snapshot is not expanded. The extension abandons old results on reconnect, project switch, or loss of workspace trust. A queued request on the original Workbench may still be reviewed there until expiry; the terminal always displays that original project.

The extension host owns transport and schemas. Its webview can only request catalog IDs from the rendered view; it never receives the bearer and cannot route arbitrary RPC. Agent tools, parsed follow-ups, task artifacts, markdown links, and workspace config cannot initiate the VS Code flow or drive the approval terminal. This follows the [output-format trust rule](OUTPUT_FORMAT.md#9-security-model): model text is a proposal, not authorization. Workspace Trust is a client-side precondition, not a server authorization claim.

The security boundary is control of the Workbench process and its operator terminal. A TTY and foreground status do not prove human presence or prevent another process from driving it. Operator launch and isolation from the requester are deployment prerequisites, not properties inferred from `isatty`. VS Code must not spawn Workbench or pass its terminal input. Where these prerequisites cannot be met, require a separately controlled approval broker or native prompt whose authority is unavailable to the requesting client; until then, no installs. This does not protect against a compromised host or access to its private state.

### Shared review plan

The [desktop native dialog at #246's reviewed revision](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/blob/94d169465a14fd6a91223de4787f08a8e13f1b37/apps/shell/src/main/extensions.ts#L94-L120) names the project, permissions, 30-day MCP approval, and customized instructions affected by a restore. Both trusted surfaces should render one host-owned structured `ExtensionReviewPlan`, not independently construct the disclosures:

| Field | What the operator sees |
| --- | --- |
| Target and catalog entry | Canonical source project path, owner/project, entry ID, name and description, bundled version, and each shared permission line. |
| Payload identity | Ordered filenames and SHA-256 digests, available as details in both prompts. |
| MCP effects | Exact bundled process, callable tools, file/network/credential access, and the planned 30-day grant duration from approval. If host policy cannot honor the plan exactly, refuse rather than silently shorten, lengthen, or renew it. |
| Skill or kit effects | Names and exact operations: create, no-op, restore identical archived content, or conflict. A desktop-only plan may also name each customized instruction it will replace and disclose that the prior version stays in history. |

Plan and prompt text come from validated host state. Render bounded, escaped text; bind the approval to a digest of the exact plan and its state fence, and apply only its approved operations. Share the plan schema and field semantics, not desktop's overwrite policy. If any existing skill has different content, active or archived, Workbench must block the whole install. It must not route to desktop's [restore-and-update path](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/blob/94d169465a14fd6a91223de4787f08a8e13f1b37/apps/shell/src/runtime/extensions.ts#L161-L188). A blocked plan can explain the conflict but cannot be approved.

## Proposed RPC surface

Use the existing `POST /v1/rpc` envelope, strict schemas, bearer, origin/loopback checks, request limits and scope comparison. The server derives install scope, source and destination from the live Workbench, never from project input or an RPC path. A shared bearer can read the catalog and enqueue; it cannot cross the local approval boundary.

| Method | Parameters (besides the existing request context) | Result / effect |
| --- | --- | --- |
| `extensions.list` | None | Protocol version, opaque instance ID, catalog revision, and entries with ID, kind, name, version, permissions, and last-committed project state with its snapshot revision and timestamp. |
| `extensions.requestInstall` | Catalog ID, instance ID, catalog revision | A pending intent, opaque status handle, short human review code and expiry; no payload execution, registry write, grant or skill write. |
| `extensions.installStatus` | Opaque status handle | Retained intent state: pending, reviewing, applying, installed, already installed, declined, expired, or failed, with a bounded reason code. Unknown or purged handles (including from a previous instance) return `not_found`. Never returns a proof, key, command, private path, or raw error. |

There is deliberately no `install`, `approve`, or `revoke` RPC. Request bodies reject extra fields, including commands, URLs, paths, credentials, approval or actor claims, and caller-supplied permissions. An unknown entry, stale catalog revision or instance, or scope mismatch fails before intent creation. HTTP errors use the existing envelope: bad input/unknown method `invalid_request`, bad credential `unauthorized`, wrong scope `forbidden`, stale instance/catalog `conflict`, disabled feature `unavailable`. A successful approval that finds the exact active install already present returns `already installed`; it does not renew an active grant.

Discovery uses `extensions.list` rather than adding fields to the current strict `workbench.describe` response. For a well-formed discovery call only, the legacy unknown-method response or the new disabled response means unsupported. Auth and transport failures remain connection errors, not unsupported. Older clients continue using the unchanged RPCs. The VS Code UI keeps its current explanation when the feature is unavailable and never falls back to another installer. V1 checks a local extension host and a direct loopback endpoint. A forwarded valid bearer that reaches an enabled listener can still list the project catalog, enqueue an intent and poll a known handle for that scope. The bearer gives no authority over the operator terminal, proofs, store writes or install execution; the review code is not approval. Forwarding is unsupported, not prevented by loopback checks.

## Intent lifetime and write safety

- Keep intents in bounded Workbench memory. Bind each to the instance, exact scope, canonical source and target store identity, and catalog revision and entry. Use an opaque random status handle separate from the human code. The server expires any unapproved intent five minutes after creation, whether never opened or still on screen. Late approval writes nothing; the operator must request again. Cap each instance at eight active intents, one displayed review, and 256 active plus retained records, with request and polling rate limits. Retain terminal states and enqueue deduplication records for ten minutes after completion or expiry, then purge. If full, reject new intents rather than evict a retained response early.
- Generate one `context.request_id` per deliberate **Request install** click and pass it explicitly into the VS Code client. Its [generic call helper](https://github.com/ronavkarumsi04/MARS-Send-Youre-AI-To-Space/blob/00811030eeffaee73d627845886fc6a3f8f4f6ee/apps/vscode/src/client.ts#L123-L131) otherwise generates a new ID per call. A lost reply may retry on the same attachment, with the same ID and parameters, within five minutes of first send. Within retention, deduplicate atomically on instance, scope and request ID: identical parameters return the original handle, code and deadline, never a new intent or renewed expiry; different parameters return `conflict`. Polling uses the handle, not the enqueue request ID.
- Build the review plan from authoritative stores at review time and verify hashes without executing payloads. Bind the human choice to that plan, including its ordered payload digests, store fence, and instance/scope. Confirm once under the commit fence below before entering `applying`; expiry, loss of foreground or a changed plan requires a fresh request. Hold verified MCP bytes stable through probe and launch using packaged or verified staged files outside workspace-writable roots.
- The terminal never hands the client a redeemable approval. All handles disappear on restart; durable installed state does not. Persist a bounded host-private audit record keyed by instance, request and final intent revision, with host actor, project scope, entry/version/digest and result code. It is not a replay ledger and cannot resurrect approval. Reuse MCP trust audit events for grant transitions. Never record credentials, review codes, approval proofs, terminal paths or raw request bytes in extension-install audit records.

### Reads and timeouts during install

Do not reuse desktop's [status implementation](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/blob/94d169465a14fd6a91223de4787f08a8e13f1b37/apps/shell/src/runtime/extensions.ts#L126-L134): its skill reads [take the writer lock and recover state](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/blob/94d169465a14fd6a91223de4787f08a8e13f1b37/packages/skills/src/store.ts#L484-L488), and opening the [MCP control plane can create a signing key](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/blob/94d169465a14fd6a91223de4787f08a8e13f1b37/packages/mcp-client/src/host.ts#L158-L163).

Instead, host-side writers publish an immutable snapshot at startup after recovery and after each catalog-relevant commit, including CLI revoke, runtime supersession and skill changes. Each generation records the project/store binding, catalog revision, committed skill, registry and trust revisions, and timestamp. The publisher atomically replaces a private file; each RPC validates the binding and catalog before serving it under the live instance ID. Entries describe the committed installed, expired, conflicting or unavailable state; known grant expiry can be evaluated from its timestamp without a probe.

`extensions.list` reads only this bounded projection. It takes no writer lock, runs no recovery, initializes no trust objects, probes nothing and writes nothing. While a write is applying, readers can see the last published generation, not staged config or partial kits. A durable dirty marker precedes store mutation and is cleared only after successful publication. If a writer exits before publishing and clearing the marker, a host-side recovery worker rebuilds the projection under the write fence, never in the RPC. Until a fresh generation is available, report the old generation as stale (or state unknown if none is valid), not an empty project or a current install. Display state never authorizes approval or runtime use.

The [reviewed desktop IPC revision](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/blob/94d169465a14fd6a91223de4787f08a8e13f1b37/apps/shell/src/main/local-workbench.ts#L107-L130) still serializes requests, but now reports unknown status after its wait deadline and holds the fence for a late reply or child exit. Here, enqueue returns before apply and status polling reads memory without waiting for the probe or writer lock. A client timeout does not cancel apply or set `failed`; only a definitive Workbench outcome can do that.

A retained request that missed its approval deadline returns the `expired` state. An unknown or purged handle returns `not_found` (HTTP 404), not `failed`. On `not_found`, restart or exhausted retry window, refresh the committed catalog and require a deliberate new request if needed; never silently re-enqueue with a new ID.

## Reuse and activation

**One catalog.** Extract #246's release-owned manifest, assets and review-plan model into a shared host-side module usable by both packagers. The Electron IPC and Workbench terminal stay distinct approval adapters. Both packages ship the same entry IDs, versions, bytes, permissions and SHA-256 digests; each server resolves from its local copy. A release test compares the catalogs and verifies all asset hashes from packaged artifacts without a source checkout. A permission or asset change produces a new catalog revision and needs fresh approval. Verified here means release-bundled, reviewed and digest checked, not publisher certification or proof that a process is OS-sandboxed.

**MCP.** Use the existing [integration trust and MCP client](INTEGRATION_TRUST.md). The opt-in Workbench owns one dedicated project-private catalog MCP state directory; install, runtime load, and CLI revocation address that same directory and exact scope. In v1 the flag is incompatible with an externally configured `--mcp-state-dir` rather than silently replacing or merging existing registries. Desktop keeps the state of its own managed Workbench; attaching to another process never imports desktop grants.

After explicit approval, use the fixed, host-selected stdio config (no credentials, no inherited project environment or env-file loading), verify the payload again, and only then permit the descriptor probe, which can start the bundled process. Match the probe to the reviewed tool names and permission manifest. Use the existing candidate review, host proof and `admin.approve` lifecycle with its normal binding and the approved grant duration. Runtime receives only the trusted loader, per task; it enforces grant and caller capabilities and revalidates evidence on dispatch. Empty environment and pinned code do not by themselves enforce a filesystem/network sandbox; the first release is limited to the reviewed offline bundled tools and must disclose their actual runtime restrictions.

The grant is the activation point. A pending candidate and staged config must be inert before grant commit. Do not overwrite a different registered config or restore missing config under an existing active grant; ask the operator to resolve inconsistent state first. Under the same commit fence, clean up only staged changes this attempt owns and whose revisions still match; otherwise leave them non-active for inspection. Crash recovery verifies the exact config, assets and active matching grant before rebuilding the snapshot; it never completes an abandoned approval. The loader still checks live descriptor drift and records supersession. Re-enabling after revoke, drift or expiry requires fresh approval.

The operator uses the existing `mars mcp list` and `mars mcp revoke <grant-id>` commands with the Workbench's bound MCP state directory, owner and project. Workbench supplies those CLI identifiers in its operator terminal, not through RPC. Existing gate checks deny future calls and the loader aborts or discards in-flight calls on revocation; it cannot undo actions already performed.

**Skills and plugins.** Use the Workbench's existing host-owned `SkillStore` instance and eligibility rules, not the checkout, editor settings, or a new global store. Apply only the reviewed batch at its expected skill-store revision. Show a plugin as installed only when all its matching skills are present and not archived. Existing skill archival is the disable path, not MCP revocation or recursive plugin removal: kits can share skills. An install changes neither credentials nor execution capabilities.

### Project identity and commit fence

[CLI location resolution](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/blob/94d169465a14fd6a91223de4787f08a8e13f1b37/apps/cli/src/workbench-location.ts#L23-L31) allows explicit project and state paths. Under a startup lock on the canonical, host-private state directory, initialize a versioned binding only for fresh state. Persist the exact scope, canonical source worktree, canonical state root, and a generated store ID, and have the dedicated MCP directory reference that same binding. Resolve and verify the binding before opening stores or keys, including for CLI commands targeting that MCP directory. The CLI checks its requested scope and resolved directory against the binding, not its current directory. Refuse mismatches, insecure roots, unknown binding versions, and nonempty unbound state; use a fresh state directory or a separately reviewed migration. Enforce the binding whenever opening marked state, even without the install flag.

Desktop currently [probes, registers and approves separately](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/blob/94d169465a14fd6a91223de4787f08a8e13f1b37/apps/shell/src/runtime/extensions.ts#L190-L215). Its [registry upsert](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/blob/94d169465a14fd6a91223de4787f08a8e13f1b37/packages/mcp-client/src/registry.ts#L243-L249) overwrites within the registry lock without comparing an expected revision. Do not use that sequence unguarded:

1. **Capture the fence.** Hold one exclusive OS-backed interprocess lock on a stable file in the canonical project state root. It is released on process exit, never stolen by age. Always take it before a registry, trust or skill store lock; take those inner locks one at a time and never acquire the project lock from an inner callback. Capture the catalog revision and ordered payload digests, existing `SkillStore` revision, new monotonic MCP registry revision and integration-trust store revision. Bind the relevant member hashes/archive states, registry config and grant/review IDs and revisions (or absence), plus the project/store binding. Hash that tuple and the plan together with the instance and per-intent review revision. Release the lock before waiting for the operator.
2. **Consume once.** Reacquire the project lock and check the original foreground terminal, deadline, full fence and plan. Compare-and-swap only that intent from its reviewed revision to a new `applying` revision before releasing the lock. The approved MCP descriptor probe is bounded and runs outside the lock without registry or trust writes, so a concurrent revoke need not wait for it. No other intent can use that approval, even if the probe fails.
3. **Commit under the fence.** Reacquire the same lock and recheck the full fence and exact applying intent before any durable mutation. Mark the projection dirty. For MCP, submit the candidate at the reviewed trust revision, conditionally insert or retain only the exact registry config at the reviewed registry revision, then approve using the resulting trust-store revision and `admin.approve`'s expected review revision. For skills, pass the reviewed revision to `applyBatch`. Hold the project lock through commit, outcome recording and publication. The instance-local intent lock, if needed, is taken only inside the project lock when both are needed and never held across I/O; enqueue and status need only the intent state. If any fence member changed, fail with a conflict that requires fresh review. If an outcome is uncertain, reconcile committed state before finalizing it; never replay the approval.
4. **Include every writer.** Bound-state write APIs must require that lock for registration, CLI revoke, trust drift/audit mutations and skill writes, including the curator. The [CLI revoke](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/blob/94d169465a14fd6a91223de4787f08a8e13f1b37/apps/cli/src/mcp.ts#L439-L490) must take it before reading and signing the target grant revision. If revoke wins, the reviewed trust revision no longer matches; if install wins, revoke acts on the specified current grant or rejects a stale ID, never reports having revoked a replacement. Existing inner locks and revision checks stay in place. An unmanaged writer with filesystem access can bypass an advisory lock; only enable installs on state with compatible writers under operator control. Never expose that state to agent-writable roots or reuse it with legacy writers.

Restarting without the opt-in flag disables the RPC feature and stops this catalog MCP loader from exposing tools in that Workbench. It does not erase grants or skill content. Use revocation or skill archival to disable an individual install durably.

## Alternatives and release gates

| Alternative | Why not v1 |
| --- | --- |
| Existing bearer plus a VS Code modal and an `approved` value | The server cannot tell a clicked modal from an HTTP client. A nonce issued to the same bearer only adds replay protection, not a separate authority. |
| Reuse Electron IPC from VS Code | It targets a desktop-managed child process, not the Workbench VS Code attached to. |
| Dedicated local approval broker for an editor-only flow | Could remove the terminal handoff, but would need separate enrollment and a proof the requester cannot mint. A follow-up design, not required here. |

Approve this proposal only if the extra terminal step is acceptable for the first release. If editor-only or unattended installs are required, do not substitute a bearer-authenticated commit; return for a separate approval-boundary design. The desktop installer owner reviews the shared catalog, approval boundary and trust integration before implementation.

- **RPC/host:** Test auth and scope, forwarded-bearer request without approval, expiry both unopened and on screen, pipe/background launch, foreground loss before consumption, and terminal cancel. Drop an enqueue reply and verify one intent survives the same-ID retry; verify conflict for changed parameters, retained `expired` and purged `not_found`.
- **Packaging/state:** Exercise all packaged entries and compare the rendered plan fields, including grant duration and skill operations. Test differing archived and active skills blocking the whole kit. Delay a real apply beyond the client timeout: listing and polling remain available without recovery, key creation, probes or writer-lock acquisition. Verify no partial state is published, including after injected failures and restart.
- **Runtime/lifecycle:** Confirm real local VS Code installs and runtime admission, then revoke via a separate CLI process during review and commit, covering both lock orderings and in-flight denial. Attempt state reuse by a different source or scope via explicit overrides; it must fail before writes. Check no hot-add and that remote, untrusted, and headless paths stay disabled. These are implementation acceptance tests, not results from this design PR.
