# Proposal: Install verified extensions from VS Code through Workbench

## Decision requested

1. **Who can call it?** A client with the current Workbench bearer and exact server-owned project scope can list, request, and track an install on an opted-in local Workbench. The MARS VS Code extension host is the intended client, not a privileged identity: another holder of that bearer can also request an install. **No RPC caller can approve it, install anything directly, or issue an MCP grant.**
2. **What replaces the native approval step?** The human operator reviews one pending request in the foreground terminal that started `mars serve`. It shows the same project and permission details as the desktop native dialog. Only explicit terminal approval can start the install, and unapproved requests expire after five minutes. The VS Code button, Workspace Trust, and any webview or model message are not consent.
3. **Does it reuse the same catalog and grant/revocation path?** Yes. Desktop and Workbench ship the same release-owned catalog and SHA-256-pinned payloads from [desktop PR #246](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/pull/246), not two copies of the definitions. MCP uses the existing host-signed review, grant, loader, and `mars mcp revoke` path in the target project's private state. Skills and plugins use that Workbench's existing skill store; plugins are bundles of instructions, not executable extensions.

**Status:** Proposed for design review. This does not change #246, the [VS Code redesign PR](https://github.com/ronavkarumsi04/MARS-Send-Youre-AI-To-Space/pull/10), or any runtime behavior.

## Scope and baseline

The first release supports a single-user, local `mars serve` instance launched with an explicit operator flag (proposed: `--verified-extensions`) from a foreground host terminal. The desktop managed Workbench keeps using its existing native dialog and IPC. VS Code Remote, remote or shared servers, forwarded/proxied deployments, remote execution workspaces, and unattended processes are not supported. No marketplace, third-party downloads, URLs, executable plugin hooks, automatic updates or grant renewals, global installation, or Assistant chat tool enablement are proposed.

Today [Workbench RPC](WORKBENCH_RPC.md) is a loopback JSON RPC server with a per-start bearer and exact scope checks. The [VS Code transport](../apps/vscode/src/extension.ts) captures the bearer from SecretStorage on connect. Neither mechanism identifies a human or proves that a dialog appeared. The desktop installer has a trusted native confirmation before the Workbench receives a catalog ID over its private channel. This proposal preserves that separation using an operator-controlled terminal rather than teaching the Workbench to trust a client assertion.

## User flow and approval boundary

1. The operator starts the opted-in Workbench in a host terminal they control, separate from the editor and agent runtime. The terminal announces that it can review requests. Without a live interactive terminal or usable project-private stores, the install feature stays unavailable; losing the terminal invalidates pending reviews. There is no piped, headless, or environment-variable approval path.
2. In a trusted, local desktop VS Code workspace, the extension host discovers support and shows the Workbench's project label and catalog. A deliberate **Request install** click sends a catalog ID; the host validates it against the current catalog and attachment. The page shows a short, expiring review code and tells the operator to switch to the Workbench terminal. It does not open a terminal, paste or run a command, or display an `Approve` action.
3. The operator enters the code in the Workbench's own review prompt. Incoming requests do not pop a prompt or print arbitrary text. Match the [desktop native dialog](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/blob/31b3dc370c48dd2e1d86ac3f44e36c7f538138c2/apps/shell/src/main/extensions.ts#L67-L82): show the entry name and description, MARS bundle version, the actual target source project path, and every permission line from the shared catalog. Also show the server-owned owner/project IDs and the exact proposed effects: for MCP, the bundled process and callable tools plus file/network/credential access; for skills or plugins, the named instructions added or restored. Project and catalog text are bounded and escaped for terminal display. The code selects a request, not a permission. The operator must choose **Add to project** explicitly; Cancel, Enter without a choice, timeout, or lost terminal input prevents approval.
4. Workbench consumes the approval internally and executes the reviewed plan once. VS Code polls for the result using the original connection and refreshes the catalog. New tasks can use the installed content; an existing task's tool or instruction snapshot is not expanded. The extension abandons old results on reconnect, project switch, or loss of workspace trust. A queued request on the original Workbench may still be reviewed there until expiry; the terminal always displays that original project.

The extension host owns transport and schemas. Its webview can only request catalog IDs from the rendered view; it never receives the bearer and cannot route arbitrary RPC. Agent tools, parsed follow-ups, task artifacts, markdown links, and workspace config cannot initiate the VS Code flow or drive the approval terminal. This follows the [output-format trust rule](OUTPUT_FORMAT.md#9-security-model): model text is a proposal, not authorization. Workspace Trust is a client-side precondition, not a server authorization claim.

The security boundary is control of the Workbench process and its operator terminal, not a claim that a TTY proves human presence. This design does not protect against a compromised host or a process with access to the operator's terminal or private state. Do not launch the approval terminal from an agent, workspace task, or editor terminal that untrusted code can drive.

## Proposed RPC surface

Use the existing `POST /v1/rpc` envelope, strict schemas, bearer, origin/loopback checks, request limits and scope comparison. The server derives install scope, source and destination from the live Workbench, never from project input or an RPC path. A shared bearer can read the catalog and enqueue; it cannot cross the local approval boundary.

| Method | Parameters (besides the existing request context) | Result / effect |
| --- | --- | --- |
| `extensions.list` | None | Protocol version, opaque instance ID, catalog revision, and entries with ID, kind, name, version, permission summary, and current project state. No spawn, discovery, grant write, or store changes. |
| `extensions.requestInstall` | Catalog ID, instance ID, catalog revision | A pending intent, opaque status handle, short human review code and expiry; no payload execution, registry write, grant or skill write. |
| `extensions.installStatus` | Opaque status handle | Pending, reviewing, applying, installed, already installed, declined, expired, or failed, with a bounded reason code. Never returns a proof, key, command, private path, or raw error. |

There is deliberately no `install`, `approve`, or `revoke` RPC. Request bodies reject extra fields, including commands, URLs, paths, credentials, approval or actor claims, and caller-supplied permissions. An unknown entry, stale catalog revision or instance, or scope mismatch fails before intent creation. HTTP errors use the existing envelope: bad input/unknown method `invalid_request`, bad credential `unauthorized`, wrong scope `forbidden`, stale instance/catalog `conflict`, disabled feature `unavailable`. A successful approval that finds the exact active install already present returns `already installed`; it does not renew an active grant.

Discovery uses `extensions.list` rather than adding fields to the current strict `workbench.describe` response. For a well-formed discovery call only, the legacy unknown-method response or the new disabled response means unsupported. Auth and transport failures remain connection errors, not unsupported. Older clients continue using the unchanged RPCs. The VS Code UI keeps its current explanation when the feature is unavailable and never falls back to another installer. V1 checks a local extension host and a direct loopback endpoint; a deliberately forwarded bearer can still reach a loopback listener and queue a request. It cannot approve one. Loopback is not a client identity or a defense against an operator exposing the port.

## Intent lifetime and write safety

- Keep intents in bounded Workbench memory. Bind each to the instance, exact owner/project scope, canonical source and target store identity, catalog revision, entry/version, ordered payload digests and permission plan. Use an opaque random status handle, separate from the human code. The server expires any unapproved intent five minutes after creation, whether it was never opened or is still on screen. A late approval writes nothing; the operator must request again. Allow at most eight outstanding requests per instance, one review at a time, and per-instance rate limits for requests and polling. Retain final results briefly, then purge. Retries with the same request ID and parameters return the same result during retention; reject reuse with different parameters.
- Before presenting a review, resolve the current host-owned plan and check payload hashes without executing them. At confirmation, atomically transition that exact pending review to applying and recheck expiry, project/Workbench instance, catalog, payloads, and relevant store revisions. A changed plan or conflicting write requires a fresh review, not a silent rebase. Hold the verified MCP bytes stable through probe and launch using packaged or verified staged files outside workspace-writable roots; never run from a path whose contents an agent can replace.
- The terminal never hands the client a redeemable approval. Pending intents disappear on restart; durable installed state does not. Persist a bounded host-private outcome record with instance/request correlation, host actor, project scope, entry/version/digest, and result code. Reuse MCP trust audit events for grant transitions. Never record credentials, review codes, approval proofs, terminal paths or raw request bytes in extension-install audit records.

### Reads and timeouts during install

Unlike the [desktop IPC adapter](https://github.com/tanaypatel917-lab/MARS-Send-Youre-AI-To-Space/blob/31b3dc370c48dd2e1d86ac3f44e36c7f538138c2/apps/shell/src/main/local-workbench.ts#L101-L127), this API does not wait for installation in the request call. Listing and polling stay available while the approved install is applying; neither waits for the install's probe or writer lock. List reflects committed state, not staged writes, while the status handle reports `applying`. A slow or disconnected client does not cancel the install or turn it into `failed`: only the Workbench's definitive outcome sets a final result. If the request reply times out before yielding a handle, retry with the same request ID; otherwise poll the existing handle. After a restart or expired result handle, refresh the catalog before offering a new request. The five-minute deadline governs consent, not execution.

## Reuse and activation

**One catalog.** Extract #246's release-owned manifest, assets and project install logic behind a shared host-side module usable by both packagers. The Electron IPC and Workbench terminal stay distinct approval adapters. Both packages ship the same entry IDs, versions, bytes, permissions and SHA-256 digests; each server resolves from its local copy. A release test compares the catalogs and verifies all asset hashes from packaged artifacts without a source checkout. A permission or asset change produces a new catalog revision and needs fresh approval. Verified here means release-bundled, reviewed and digest checked, not publisher certification or proof that a process is OS-sandboxed.

**MCP.** Use the existing [integration trust and MCP client](INTEGRATION_TRUST.md). The opt-in Workbench owns one dedicated project-private catalog MCP state directory; install, runtime load, and CLI revocation address that same directory and exact scope. In v1 the flag is incompatible with an externally configured `--mcp-state-dir` rather than silently replacing or merging existing registries. Desktop keeps the state of its own managed Workbench; attaching to another process never imports desktop grants.

After explicit approval, use the fixed, host-selected stdio config (no credentials, no inherited project environment or env-file loading), verify the payload again, and only then permit the descriptor probe, which can start the bundled process. Match the probe to the reviewed tool names and permission manifest. Use the existing candidate review, registry, host proof and `admin.approve` lifecycle with its normal binding and TTL. Runtime receives only the trusted loader, per task; it enforces grant and caller capabilities and revalidates evidence on dispatch. Empty environment and pinned code do not by themselves enforce a filesystem/network sandbox; the first release is limited to the reviewed offline bundled tools and must disclose their actual runtime restrictions.

The grant is the activation point. Installation must fence competing registry and trust writes and never overwrite a different registered config or restore missing config under an existing active grant; require the operator to resolve inconsistent state first. Before the new grant exists, a pending review/config is inert. Clean up only install-owned staged changes if the expected revision still matches, and otherwise leave them non-active for operator inspection. After a crash, derive installed state from the exact catalog config, verified assets and active matching grant, not from an install receipt. List is a read-only snapshot: it can report static drift or recorded grant state without probing a process. The loader still checks live descriptor drift at admission and dispatch and records supersession; an installed label is not a runtime authorization. A later re-enable requires a new terminal approval.

The operator uses the existing `mars mcp list` and `mars mcp revoke <grant-id>` commands with the Workbench's state directory, owner and project. Workbench supplies those CLI identifiers in its operator terminal, not through RPC. Existing gate checks deny future calls and the loader aborts or discards in-flight calls on revocation; it cannot undo actions already performed. Concurrent revoke and install must be ordered so an install reviewed before a conflicting revoke cannot silently replace the grant.

**Skills and plugins.** Use the Workbench's existing host-owned `SkillStore` instance and eligibility rules, not the checkout, editor settings, or a new global store. Batch all instructions with the store's expected revision. Identical active content is a no-op; restoring identical archived content is listed in the approval. Differing content at the same name or a revision conflict fails the whole batch. Show a plugin as installed only when all its matching skills are present and not archived. Existing skill archival is the disable path, not MCP revocation or recursive plugin removal: kits can share skills. An install changes neither credentials nor execution capabilities.

Restarting without the opt-in flag disables the RPC feature and stops this catalog MCP loader from exposing tools in that Workbench. It does not erase grants or skill content. Use revocation or skill archival to disable an individual install durably.

## Alternatives and release gates

| Alternative | Why not v1 |
| --- | --- |
| Existing bearer plus a VS Code modal and an `approved` value | The server cannot tell a clicked modal from an HTTP client. A nonce issued to the same bearer only adds replay protection, not a separate authority. |
| Reuse Electron IPC from VS Code | It targets a desktop-managed child process, not the Workbench VS Code attached to. |
| Dedicated local approval broker for an editor-only flow | Could remove the terminal handoff, but would need separate enrollment and a proof the requester cannot mint. A follow-up design, not required here. |

Approve this proposal only if the extra terminal step is acceptable for the first release. If editor-only or unattended installs are required, do not substitute a bearer-authenticated commit; return for a separate approval-boundary design. The desktop installer owner reviews the shared catalog, approval boundary and trust integration before implementation.

- **RPC/host:** Valid, invalid and wrong-scope bearers; legacy and disabled detection; strict input validation; no grants, probes or skill writes before approval; fake consent and status/correlation replays have no effect. Test expiry both when a request is never opened and when approval arrives late. Exercise project switch, restart, duplicate requests, concurrent confirm, and terminal cancel/closure.
- **Packaging/state:** Exercise every packaged entry and check project and permission display parity in both products. Reject byte/permission drift and registry or skill conflicts, including changes during review. Delay a real apply beyond the client timeout: list still works, status remains applying until completion, and retries do not duplicate the grant or batch. Inject failures around registration and commit; no unapproved runtime access or partial kit. Check restart reconciliation and two-project isolation.
- **Runtime/lifecycle:** Confirm one install of each kind from real local VS Code against an opted-in CLI Workbench. Run a new task with one bundled MCP, revoke through the existing CLI with the same state/scope, and verify later denial and in-flight handling. Check no hot-add to existing tasks or Assistant chat; reject remote, untrusted, and headless paths. These are implementation acceptance tests, not results from this design PR.
